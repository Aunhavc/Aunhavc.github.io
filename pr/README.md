## ติดตั้ง (ครั้งเดียว ~15 นาที)

### 1. สร้างโปรเจกต์ Supabase
เข้า [supabase.com](https://supabase.com) → New project → เลือก region **Southeast Asia (Singapore)**

> ⚠ **สร้างโปรเจกต์ใหม่แยกต่างหาก** อย่าใช้โปรเจกต์เดียวกับ Ultimate ADHD Planner ที่อยู่ใน repo นี้
> ข้อมูลผู้ขาย ราคา และผู้อนุมัติของบริษัท ไม่ควรอยู่รวมกับข้อมูลลูกค้าของสินค้าอีกตัว

### 2. สร้างตาราง
Supabase Dashboard → **SQL Editor** → New query → วางไฟล์ [`schema.sql`](schema.sql) ทั้งไฟล์ → Run
(รันซ้ำได้ ไม่พัง)

### 3. กรอก `config.js`
Project Settings → API → คัดลอก **Project URL** กับ **anon public key** มาใส่:

```js
window.PR_CONFIG = {
  SUPABASE_URL:      'https://xxxxxxxx.supabase.co',
  SUPABASE_ANON_KEY: 'eyJhbGciOi...',
  ORG_NAME: 'บริษัท สมใจบิซกรุ๊ป จำกัด'
};
```

คีย์ 2 ตัวนี้ **เปิดเผยได้** ออกแบบมาให้ฝังในหน้าเว็บ ความปลอดภัยอยู่ที่ RLS ในฐานข้อมูล
**ห้ามใส่ `service_role` key เด็ดขาด** — ตัวนั้นข้าม RLS ได้ทั้งหมด

### 4. ปิดการยืนยันอีเมล (ถ้าไม่อยากตั้งค่า SMTP)
Authentication → Providers → Email → ปิด **Confirm email**
ไม่ปิดก็ได้ แต่ต้องตั้ง SMTP เอง ไม่งั้นคนสมัครแล้วเข้าใช้ไม่ได้

### 5. ตั้งตัวเองเป็นแอดมิน
เปิด `pr/index.html` → สมัครด้วยอีเมลบริษัท → กลับไปที่ SQL Editor รันคำสั่งนี้ (แก้อีเมลก่อน):

```sql
update pr_member
   set role='admin', full_name='ชื่อ นามสกุล', position='ผู้จัดการฝ่ายไอที',
       department='ฝ่ายเทคโนโลยีสารสนเทศ', dept_code='IT'
 where user_id = (select id from auth.users where email='you@company.com');
```

จากนั้นเมนู **จัดการผู้ใช้** จะโผล่ขึ้นมา ใช้ตั้งฝ่าย/สิทธิ์ให้คนอื่นได้จากหน้าเว็บเลย

## สิทธิ์ผู้ใช้

| สิทธิ์ | ทำอะไรได้ |
|---|---|
| `staff` (ผู้ขอซื้อ) | สร้าง/แก้ใบของตัวเอง · เห็นใบของฝ่ายตัวเอง |
| `it` (ฝ่าย IT) | เห็นทุกใบ · ให้ความเห็น เห็นชอบ/ไม่เห็นชอบ |
| `approver` (ผู้อนุมัติ) | เห็นทุกใบ · อนุมัติ/ตีกลับ · แปะเลข SAP |
| `admin` | ทุกอย่าง + จัดการผู้ใช้ |

> **`dept_code` สำคัญ** — เลขที่เอกสารออกจากค่านี้ (`PR-2026-`**`IT`**`-0001`)
> ตั้งให้ครบก่อนให้คนเริ่มใช้ ไม่งั้นทุกฝ่ายจะได้เลขชุด `GEN` ปนกัน

## เส้นทางเอกสาร

```
ร่าง ──(ส่งอนุมัติ)──▶ รออนุมัติ ──▶ อนุมัติแล้ว ──▶ พิมพ์ A4 ──▶ เก็บลายเซ็นจริงบนกระดาษ
 ▲                        │
 └────(ตีกลับ+เหตุผล)─────┘
```

**กดส่งอนุมัติแล้วแก้ไม่ได้** จนกว่าจะถูกตีกลับ — บังคับที่ฐานข้อมูล (RLS) ไม่ใช่แค่ซ่อนปุ่ม
สายอนุมัติหลายชั้นของผู้บริหารยังเกิดบนกระดาษเหมือนเดิม ระบบนี้แค่ทำให้ใบที่พิมพ์ออกมาถูกต้องและตามได้

## จุดที่ออกแบบไว้กันผู้ตรวจสอบตีตก

1. **ใบล็อกหลังส่งอนุมัติ** — บังคับด้วย RLS policy ฝั่งฐานข้อมูล เปิด DevTools แก้ก็ไม่ผ่าน
2. **ทุกใบที่พิมพ์มี `เลขที่เอกสาร · ครั้งที่ N · เวลาที่พิมพ์` ที่ท้ายกระดาษ**
   ไม่งั้นเซ็นกระดาษครั้งที่ 1 แต่ในระบบเป็นครั้งที่ 3 แล้วพิสูจน์ไม่ได้ว่าอนุมัติอะไร
3. **ยอดเงินทุกช่องคำนวณในฐานข้อมูล** (generated column) ไม่ใช่ใน JavaScript
   เลขบนกระดาษกับเลขใน DB จึงตรงกันเสมอ
4. **`pr_log` เขียนได้อย่างเดียว** ไม่มี policy ให้ update/delete — ประวัติลบไม่ได้

## แก้ฟอร์มเมื่อ HR เปลี่ยนแบบ

| อยากแก้อะไร | แก้ที่ไฟล์ |
|---|---|
| ชื่อ/ตำแหน่งผู้เซ็น, เงื่อนไข 3 ข้อ, รหัสฟอร์ม, วงเงินผู้จัดการ | `form-config.js` |
| เลย์เอาต์กระดาษ ขนาดช่อง เส้นตาราง | `print-render.js` + `print.css` |
| ช่องกรอกในหน้าเว็บ | `edit.js` |
| เพิ่ม/ลดคอลัมน์ในฐานข้อมูล | `schema.sql` แล้วรันใหม่ |

**ดูตัวอย่างใบพิมพ์โดยไม่ต้องติดตั้งอะไร:** เปิด [`preview.html`](preview.html) — ใช้ข้อมูลสมมติ ไม่ต่อฐานข้อมูล
เหมาะกับตอนเอาไปให้ HR/จัดซื้อดูว่าหน้าตาตรงของเดิมไหม ก่อนลงมือติดตั้งจริง

## ข้อจำกัดที่ต้องรู้ก่อนใช้

- **ไลบรารี Supabase โหลดจาก CDN ภายนอก (`esm.sh`)** — ถ้าเน็ตบริษัทบล็อก หน้าเว็บจะเปิดไม่ขึ้น
  (มีตัวดักขึ้นข้อความบอกสาเหตุให้แล้วใน `boot-check.js`)
  ถ้าอยากตัดความเสี่ยงนี้ ให้โหลดไฟล์ไลบรารีมาเก็บไว้ใน repo แล้วชี้ path มาที่ไฟล์ในเครื่องแทน
- **ข้อมูลอยู่บน Supabase (cloud)** — ถ้านโยบายบริษัทห้ามข้อมูลผู้ขาย/ราคาออกนอกองค์กร ต้องเปลี่ยนเป็น self-host
- **ยังไม่ได้ทดสอบกับผู้ใช้จริง** — ทดลองกับ 2-3 ใบก่อนประกาศใช้ทั้งบริษัท
